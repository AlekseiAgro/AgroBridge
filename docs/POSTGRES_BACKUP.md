# AgroBridge PostgreSQL backup tool

Phase 1 foundation only. This document describes the isolated backup utility in `apps/db-backup`.

**Production backup is not active.** This PR does not create a Railway Cron service, does not create a production R2 bucket, and does not connect to production PostgreSQL.

## Purpose

Provide a read-only `pg_dump` pipeline that can later run as a Railway Cron service:

```
pg_dump -Fc → verify → upload dump+json → update manifest → retention → exit 0
```

On failure the process exits `1` and may send a Resend alert. It never runs Prisma, seeds, cleanup scripts, or the API entrypoint.

## Architecture

- Isolated package: `@agrobridge/db-backup`
- Isolated image: `apps/db-backup/Dockerfile`
- Railway config: `apps/db-backup/railway.toml` (same pattern as `api` / `web`)
- Not part of the NestJS API runtime
- PostgreSQL is only read (`pg_dump`, `SHOW server_version`)
- Object storage uses the `BACKUP_R2_*` namespace, never media `S3_*` keys

## PostgreSQL client version

The production PostgreSQL **major version is not verified**.

The image defaults to client **16** only because local `docker-compose.yml` uses `postgres:16-alpine`. That is not a production claim.

Build-time overrides:

```bash
# context is the repository root — do not build with -f from apps/db-backup as context
docker build -f apps/db-backup/Dockerfile \
  --build-arg PG_CLIENT_MAJOR=16 \
  --build-arg PG_DUMP_IMAGE_TAG=16-alpine \
  -t agrobridge-db-backup .
```

After the live server major is known, rebuild with the matching `PG_CLIENT_MAJOR`. The tool fails clearly if `pg_dump` is older than the server major.

## Environment variables

| Variable | Purpose | Default |
|---|---|---|
| `DATABASE_URL` | PostgreSQL URL (Prisma `?schema=public` is stripped) | required |
| `BACKUP_ENVIRONMENT` | Object prefix (`production`, `local`, …) | `production` |
| `BACKUP_KIND` | `daily` / `weekly` / `monthly` / `manual` | `daily` |
| `BACKUP_DRY_RUN` | Verify dump locally; no remote writes/deletes | unset |
| `BACKUP_STORAGE` | `s3` / `fs` / `memory` | `s3` |
| `BACKUP_FS_ROOT` | Local directory for `fs` storage | required for `fs` |
| `BACKUP_MIN_BYTES` | Minimum dump size | `1024` |
| `BACKUP_TIMEOUT_MS` | Overall timeout | `600000` |
| `BACKUP_KEEP_DAILY` | Daily retention | `7` |
| `BACKUP_KEEP_WEEKLY` | Weekly retention | `4` |
| `BACKUP_KEEP_MONTHLY` | Monthly retention | `3` |
| `BACKUP_R2_ENDPOINT` | S3-compatible endpoint | — |
| `BACKUP_R2_ACCESS_KEY_ID` | Backup-only access key | — |
| `BACKUP_R2_SECRET_ACCESS_KEY` | Backup-only secret | — |
| `BACKUP_R2_BUCKET` | Dedicated private bucket | — |
| `BACKUP_R2_REGION` | Region | `auto` |
| `RESEND_API_KEY` | Failure alerts | optional |
| `BACKUP_ALERT_EMAIL` | Failure recipient | optional |
| `MAIL_FROM` | Failure From | optional |
| `PGSSLMODE` | Passed through libpq if not in the URL | — |

Do not set media `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` on this tool.

## Local testing

Unit tests (no Docker, no production):

```bash
pnpm --filter @agrobridge/db-backup test
pnpm --filter @agrobridge/db-backup lint
```

Optional Docker integration (ephemeral Postgres, never production):

```bash
pnpm --filter @agrobridge/db-backup build
BACKUP_INTEGRATION=1 pnpm --filter @agrobridge/db-backup test:integration
# or
sh apps/db-backup/scripts/local-integration.sh
```

Dry-run against a **local** database:

```bash
BACKUP_DRY_RUN=true \
BACKUP_STORAGE=fs \
BACKUP_FS_ROOT=/tmp/agrobridge-backups \
BACKUP_ENVIRONMENT=local \
BACKUP_KIND=daily \
DATABASE_URL='postgresql://agrobridge:agrobridge@127.0.0.1:5432/agrobridge?schema=public' \
pnpm --filter @agrobridge/db-backup start
```

Manual locked backup (same binary):

```bash
BACKUP_KIND=manual BACKUP_STORAGE=fs BACKUP_FS_ROOT=/tmp/agrobridge-backups \
BACKUP_ENVIRONMENT=local DATABASE_URL='postgresql://…' \
pnpm --filter @agrobridge/db-backup start
```

## Retention

Retention reads `production/manifest.json` (or `<env>/manifest.json`). It does **not** delete “everything older than N days” by filename.

- Keep 7 newest daily, 4 newest weekly, 3 newest monthly
- A dump tagged daily+weekly is kept if **either** window still includes it
- `BACKUP_KIND=manual` sets `locked: true` and is never auto-deleted

## Security

- `pg_dump` / `pg_restore` / `psql` are spawned with argument arrays, not a shell
- Credentials go through libpq environment variables, not argv
- Logs redact URLs and secret-shaped strings
- Temporary directories are mode `0700` and deleted on success and failure
- Object keys are generated by the tool; `..` is rejected
- Failure email contains only UTC time, environment, step, safe message, optional size

## Restore preparation

Phase 1 does **not** automate restore. A later drill should:

1. Download a dump from the backup bucket
2. `pg_restore --list` then restore into a **new** PostgreSQL
3. Point a temporary API at that database
4. Never run this tool with a production `DATABASE_URL` until Phase 3+

Because the API still runs `prisma migrate deploy` on start, restore of an older dump must be paired with a compatible API image. See the backup architecture notes: an old database under a newer API image will re-apply forward migrations.

## Railway build settings

The Dockerfile is written for a **repository-root** Docker context, like `apps/api/Dockerfile`. It copies `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, and `apps/db-backup/**`.

If Railway **Root Directory** is `apps/db-backup`, the build context is only that folder and the build fails with:

```text
COPY apps/db-backup ./apps/db-backup
"/apps/db-backup": not found
```

Required dashboard settings (do not change `api` / `web`):

| Setting | Value |
|---------|--------|
| Builder | **Dockerfile** |
| Dockerfile path | `apps/db-backup/Dockerfile` |
| Root Directory | *(leave empty — repo root)* |
| Watch Paths | `/apps/db-backup/**` |
| Config-as-code path | `apps/db-backup/railway.toml` |

`railway.toml` cannot set Root Directory. Clearing Root Directory is a dashboard setting.

Do not point this service at `apps/api/docker-entrypoint.sh`. Do not add `apps/api` or `packages/shared` to Watch Paths: the backup package does not depend on them.
